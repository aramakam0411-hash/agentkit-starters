# Client demo handoff

Read the agreed brief and actual delivery evidence. Identify the one result the client should try first. Do not add marketing claims, invented testimonials, conversion improvements or readiness promises to make the handoff sound stronger.

Write a short walkthrough with the real access route, one input and the output the client should observe. Verify the link if tools permit. If access is local, explain how the client can try it; do not imply a local preview is hosted. Use [the handoff sheet](../../templates/client-handoff.md) when useful.

Explain scope through visible behavior. Mark sample data, simulated integrations, unavailable features and checks not run. Describe an unfinished payment or booking connection as unfinished even when its button looks complete. State the practical consequence, such as requests being drafted but not sent.

List decisions the client actually needs to make next: their real business content, chosen service accounts, domain or agreed deployment. Reuse existing authorization and completed decisions. Do not turn a demo handoff into a new paid service, deployment, credential exchange or contact campaign.

Deliver the walkthrough, a compact current-status section and one next step. If the client wants a message to forward, provide copy they can review; sending it requires the user's actual authorization. Ask for feedback about whether the task was completed and where the person got stuck, instead of a generic request to approve the appearance.
