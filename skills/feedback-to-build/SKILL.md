# Feedback to build

Read the original task, current behavior and actual feedback. Separate the person's observation from your interpretation: “I cannot find the price” is evidence; “the entire layout needs replacing” is a proposed solution. Preserve explicit changes the user has already requested.

Group feedback by the user task it affects. Prioritize a blocked core task or misleading result before optional polish. Do not treat every comment as a new feature, assume all users agree, or turn a single opinion into measured conversion data.

Use [the change sheet](../../templates/feedback-change.md) for the next useful change. State the current behavior, desired behavior and an observable acceptance check. For “make it easier,” choose a concrete interpretation from the evidence, such as finding the booking action on a phone without scrolling past unrelated content. Ask one focused question only when different interpretations would change the core result.

Keep the brief small enough to implement and review as one coherent change. Include the original working path that must still work. Preserve the user's files, content and settled choices; do not use feedback as permission for an unrelated rewrite or live publication.

If asked to implement, make the change and test the affected path using available tools. Return the useful difference, the check actually run and remaining uncertainty. Keep unresolved feedback recorded, without promising that everything has been fixed or turning the backlog into automatic authorization.
